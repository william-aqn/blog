# Часть 2. PHP 7.4 на CentOS 7: те же CVE, но ветка давно мертва

Это продолжение статьи [«PHP 8.2.35 на CentOS 7: закрываем CVE-2026-109618 и CVE-2026-109619 без обновления Bitrix»](../_fix_php/README.md). В первой части мы пересобрали 8.2.35 для сервера на PHP 8.2. Здесь речь о втором сервере: на нём до сих пор работает **PHP 7.4**, а официального релиза с исправлением для этой ветки нет и не будет.

Общие вещи — vault для CentOS 7, архив EPEL, `rpm2cpio` вместо `rpm -i`, полный рестарт вместо graceful — подробно разобраны в первой части. Здесь описано только то, чем отличается 7.4. Все скрипты и собранные пакеты лежат рядом, комплект самостоятельный.

## Коротко

- Для 7.4 (EOL с ноября 2022) upstream выпустил не релиз, а минимальный бэкпорт в ветке `PHP-7.4-CVE-2026-109618-109619` репозитория php-src. Это один коммит «Avoid state corruption via bailout»: 19 файлов, +245/−61 строк.
- remi в день релиза выложил `php-7.4.33-31.remi.src.rpm` с этим бэкпортом. На сервере стояла `7.4.33-15.el7.remi`, последняя сборка remi для EL7 (июнь 2024). Переход на `-31` заодно приносит около 40 исправлений безопасности, которые remi бэкпортировал в 2024–2026 годах.
- Пересборка под CentOS 7 идёт теми же приёмами, что в первой части, плюс одна новая ловушка: патч remi для ICU 74 всегда требует C++17.
- ABI не меняется: PECL-расширения 7.4 (apcu, memcache, geoip, mcrypt, rrd, xdebug, zip) пересобирать не нужно. Мы проверили это в том числе на бинарнике `zip.so`, снятом прямо с сервера.
- Бэкпорт для 7.4 **полностью выключает session upload progress**. Bitrix эту функцию не использует.
- Полный рестарт Apache занял около секунды, но 23 из 102 запросов в окне рестарта получили 502/504.

## Исходная ситуация

| | |
|---|---|
| ОС | CentOS 7.9 |
| Окружение | BitrixVM 7.5 |
| Веб | nginx 1.20 → Apache 2.4.6 prefork + mod_php, рядом `httpd-scale` |
| PHP | 7.4.33-15.el7.remi: 15 подпакетов, включая отдельный `php-json` |
| PECL | apcu 5.1.22, geoip 1.1.1, mcrypt 1.0.6, memcache 4.0.5.2, rrd 2.0.3, xdebug 2.9.8, zip 1.21.1 |
| OpenSSL | 1.0.2k, системный |
| Bitrix | 22.x |

## Чем 7.4 отличается от 8.2

### Откуда берётся исправление

У php.net для 7.4 нет ни тарбола, ни тега, только ветка с бэкпортом. remi приложил её к своему SRPM отдельным патчем `php-7.4-cve-2026-109618.patch`. Первая запись в changelog `7.4.33-31` датирована 21.10.2026 и прямо называет обе CVE. Скрипт `build.sh` проверяет это по changelog скачанного SRPM, а исходник `php-7.4.33.tar.xz` сверяет с sha256, который публикует php.net.

### ABI: PECL пересобирать не нужно

Заголовки движка в бэкпорте только дополняются: `zend_new_array_singleton()`, `zend_mm_safe_error_ex()`, макрос `array_init_singleton`. В `zend_types.h` меняется лишь тело макроса `HT_HASH_RESET`, раскладка структур остаётся прежней. Поэтому модули, собранные под 7.4.33-15, работают и с -31. В тесте мы проверили все 7 pecl-расширений сервера: 6 стояли в точных версиях из репозитория, а `zip.so` взяли с самого сервера.

### Что меняется в поведении

- **Session upload progress выключен насовсем.** В `ext/session/session.c` условие стало `if (!PS(rfc1867_enabled) || true) return`. Данные прогресса в `$_SESSION` больше не появляются, даже если `session.upload_progress.enabled = On`.
- **В multipart PHP сохраняет только заголовки `Content-Disposition` и `Content-Type` каждой части.** Остальные и дубликаты отбрасываются. Других PHP и не использует.
- **Меняется вывод при исчерпании `memory_limit`.** Обработку OOM переделывает исправление CVE-2026-109618.

Набор тестов PHP при сборке: из 15 901 теста 9 071 пройдено, 6 788 пропущено, 33 упали ожидаемо (помечены в самих тестах) и **9 упали**. Все 9 приходятся ровно на эти места: 8 тестов `ext/session/tests/rfc1867*.phpt` ждут данные upload progress, а `tests/lang/bug45392.phpt` ждёт прежний вывод при нехватке памяти. Обычные тесты загрузки файлов прошли.

## Шаг 0. Временные меры

Всё так же, как в первой части: [`server/mitigate.sh`](server/mitigate.sh) выключает `session.upload_progress` и снижает размер тела запроса до 64M.

```bash
LIMIT_MB=64 bash server/mitigate.sh
```

На этом сервере ни одного ответа 5xx не появилось ни до, ни после.

## Шаг 1. Сборка RPM

В [`build/`](build/) лежат:

- `Dockerfile` — то же окружение CentOS 7, что в первой части.
- `build.sh` — скачивает SRPM, проверяет в changelog упоминание CVE, сверяет исходник с php.net, вносит две правки в spec и собирает.
- `php-7.4.33-icu-check.patch` — новая правка, о ней ниже.
- `php74.spec.diff` — все изменения spec относительно remi: 3 правки.

```bash
docker build -t php74-el7-build build/
```

```bash
docker run --rm -v "$PWD/out:/out" php74-el7-build
```

На 8 vCPU установка зависимостей занимает около 4 минут, сборка — около 6, включая прогон тестов PHP. С `-e RUN_TESTS=0` тесты пропускаются. Spec remi для 7.4 управляет ими макросом `runselftest`, поэтому `--without tests`, как для 8.2, здесь ничего не отключает.

### Новые грабли

1. **ICU ≥ 74.** Та же история, что в первой части: в remi EL7 максимум `libicu73`. Снижаем требование до 73, это касается только `php-intl`.
2. **Патч remi для ICU 74 всегда требует C++17.** `php-7.4.33-icu.patch` — бэкпорт upstream-коммита GH-14002. В нём проверка написана как `test "$PKG_CONFIG icu-uc --atleast-version=74"`. Это проверка непустой строки, поэтому она истинна всегда. configure ищет C++17, в gcc 4.8 его нет, и `ext/intl` компилируется вообще без флага стандарта. Итог — ошибки `'char16_t' does not name a type` в заголовках ICU. Наш `Patch304` вызывает pkg-config вместо проверки строки, как позже сделали и в upstream. С ICU 73 тогда выбирается ветка C++11.
3. **Патч для OpenSSL 1.0.2, как у 8.2.35, не нужен.** `xp_ssl.c` в 7.4 не вызывает `ASN1_STRING_get0_data()`, а `openssl.c` содержит собственную замену. Все 332 функции OpenSSL, которые использует `libphp7.so`, экспортирует системный `libssl.so.10` / `libcrypto.so.10`. В логе сборки ноль «implicit declaration».

## Шаг 2. Проверка на копии сервера

[`test/smoke-test.sh`](test/smoke-test.sh) по умолчанию настроен на 7.4: репозиторий `remi-php74`, переход `7.4.33-15.el7.remi` → `7.4.33-31.el7.local`, в `CORE` есть `php-json`. Модуль Apache у 7.4 лежит в `15-php.conf`, а не в `20-php.conf`:

```bash
ssh root@SERVER "tar czf - /etc/php.ini /etc/php.d /etc/httpd/conf.d/php.conf /etc/httpd/conf.modules.d/15-php.conf" > prod-php-conf.tgz
```

Новая ловушка: yum **молча пропускает** версии, которых в репозитории уже нет. У нас так исчезли `php-pecl-zip-1.21.1` (осталась 1.22.x) и `php-pear-1.10.13-5`. Тест прошёл бы «зелёным», просто без zip. Поэтому такие модули копируем с сервера в `server-modules/`. Скрипт кладёт их в `/usr/lib64/php/modules` и доставляет библиотеки, которых им не хватает (для zip это `libzip.so.5`):

```bash
mkdir -p server-modules && scp root@SERVER:/usr/lib64/php/modules/zip.so server-modules/
```

```bash
docker run --rm -v "$PWD/out:/out" -v "$PWD/test:/test:ro" -v "$PWD/prod-php-conf.tgz:/prod-php-conf.tgz:ro" -v "$PWD/server-modules:/server-modules:ro" -e PECL="php-pecl-apcu-5.1.22-1.el7.remi.7.4 php-pecl-geoip-1.1.1-11.el7.remi.7.4 php-pecl-mcrypt-1.0.6-1.el7.remi.7.4 php-pecl-memcache-4.0.5.2-1.el7.remi.7.4 php-pecl-rrd-2.0.3-1.el7.remi.7.4 php-pecl-xdebug-2.9.8-1.el7.remi.7.4 php-zipstream-0.2.2-6.el7" --entrypoint bash php74-el7-build /test/smoke-test.sh
```

У нас список модулей до и после совпал. mod_php ответил `7.4.33 apache2handler`, а `zip.so` 1.21.1 с сервера создал архив через `ZipArchive` под mod_php. Пакеты 7.4.33-15 для отката скрипт сохраняет в `out/rollback/`: в `remi-php74` для EL7 они ещё есть.

## Шаг 3. Установка

Скрипт [`server/install.sh`](server/install.sh) тот же, что в первой части, но с важной поправкой. Проверка «старого кода в памяти» искала `libphp\.so`, а модуль 7.4 называется **`libphp7.so`**. На 7.4 она молча проходила бы, даже если старая библиотека осталась в памяти. Теперь регулярка такая: `libphp[0-9]*\.so(;…| (deleted))`.

```bash
scp -r out/RPMS/x86_64 out/rollback server root@SERVER:/root/php-7.4-cve/
```

```bash
ssh root@SERVER "cd /root/php-7.4-cve && bash server/install.sh x86_64"
```

Перед запуском мы искали зависшие воркеры и сначала ошиблись с порогом: «старше 25 минут» выдал **все** ~260 процессов. Их все породила graceful-перезагрузка 37 минут назад, после временных мер. Свободный prefork-воркер ждёт в `semtimedop` (accept mutex), так и должно быть. Зависшими считаются только воркеры **старше последней перезагрузки**. На этом сервере таких не было, на первом их было два.

### Результат на проде

- Скрипт отработал за 11 секунд. Обновлены 15 пакетов, список модулей прежний. Полный рестарт httpd занял 1 секунду, затем перезапустился `httpd-scale`.
- Старый код в памяти не держит ни один процесс. Vhost'ы отвечают 200/302, PHP Fatal — ноль.
- По логу nginx: до рестарта 29 548 запросов без 5xx, после — 1 459 без 5xx. В окне рестарта (около 6 секунд) **23 из 102 запросов получили 502/504**, хотя на первом сервере 502 не было. Планируйте рестарт на тихое время или настройте в nginx повтор запроса к бэкенду.
- `AH00161: server reached MaxRequestWorkers` записался один раз, в момент старта: накопившиеся за рестарт запросы пришли разом.

## Откат

```bash
bash /root/php-7.4-cve/server/rollback.sh /root/php-7.4-cve/rollback
```

Подойдут пакеты 7.4.33-15, которые сохранил `smoke-test.sh`. Rollback.sh ставит их через `rpm -Uvh --oldpackage` и полностью перезапускает Apache.

## Что дальше

- PHP 7.4 мёртв уже четыре года. Бэкпорты remi — спасательный круг, а не решение. Переход сайта на PHP 8.x потребует проверки совместимости кода и Bitrix.
- `session.upload_progress` оставляем выключенным, хотя в 7.4 он теперь и так не работает.
- Следующие бэкпорты remi (`-32`, `-33`…) собираются тем же комплектом с `-e REMI_RELEASE=32`. Для этого надо обновить проверку CVE в `build.sh` и убедиться, что `Patch304` по-прежнему накладывается.
